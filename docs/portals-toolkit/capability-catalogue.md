# Evidence-backed capability catalogue

Snapshot: `210133f4e718acb7b461f2a40c90661a40a2397f`. IDs connect source evidence to delivery decisions below. These are capability boundaries, not a promise to create one package per row.

**A** direct algorithmic translation; **B** adaptable graphics/shader implementation; **C** Three.js implementation requiring replacement/redesign; **D** unsuitable to port for this initiative. A classification describes technical portability, **not licence permission**. Split rows distinguish algorithms from their renderer plumbing.

Complexity is relative engineering scope including tests and integration: **S** small isolated algorithm; **M** multi-step algorithm/data contract; **L** substantial shader/geometry/integration work; **XL** engine-level work. These are estimates, not delivery dates. **P0** first experiment; **P1** next reusable tranche; **P2** later optional; **P3** defer/omit.

## Boundaries on what the source proves

Confirmed: procedural height recipes, erosion-like gradient damping, static adaptive tessellation, material gradients, approximate bounced colour, seeded scatter, procedural vegetation and fog/cloud approximations. A full hydraulic erosion solver, dynamic terrain streaming, general-purpose runtime mesh simplifier, physically correct atmosphere, volumetric multiple scattering, planetary curvature and persistent disk asset caching were **not established in the inspected code**. Do not market them as extracted Portals capabilities. Mesh merging, crease splitting and static LOD are not evidence of general mesh optimization.

Priority weighs reuse, visible benefit at flight distances and bounded cost. All runtime performance rankings remain engineering predictions until device measurements exist; [performance discussion](portals-architecture.md#dependencies-and-performance-implications) defines the evidence limits.
